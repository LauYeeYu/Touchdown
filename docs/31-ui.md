# 31 UI

Pages and the main flows: what each page does. How they look is in DESIGN.md.

The app is responsive: every page works in Chrome on Android. iOS is not a target. It has light and dark themes (G10), and all copy uses UK English (G9), kept in message files so it can be translated (G12, "Language" below). The quick-add flows are designed for phone first, because sightings are often logged at the airport.

## Navigation

```
Home | Flights | Spotting | Aircraft | Statistics      Add: Flight, Sighting, Spotting session
                                                       More: Import, Issues, Shared links, Aircraft types, Settings, Guide
```

A page of the main navigation (Flights, Spotting, Aircraft, Statistics) shows its name as a title on a phone only, where the navigation is at the bottom of the screen. On a computer the navigation above names it, and the title is there for screen readers (Decided, built). Home opens with its summary sentence instead.

## Airport codes

The Settings "Codes" choice (IATA, ICAO or both) applies on every page (Decided). Every code shown as text follows it, both codes when the user chose both ("LHR/EGLL → CDG/LFPG" in flight rows, facts, links, tooltips, routes in Statistics). Large type (flight and airport headers, the latest flight on Home) shows one code, ICAO when the user chose ICAO, otherwise IATA, with the other code small beneath or beside it when the user chose both. Map labels show one code. An airport named in text carries its code in parentheses: "London Heathrow (LHR)". Addresses (`/airports/LHR`) always use IATA where it is unambiguous.

## Period control

Home, Flights, Spotting, Statistics and an airport's page share one period control.

- The periods (Decided (changed), F5): every year with a flight, planned ones included, or a sighting, the current year always, even before its first record, and "All time". A later year that holds only planned flights shows them in its list and dashed on its map, and its figures stay empty until they fly.
- Segmented buttons (outlined pill, equal-width segments, a check on the selected one) while they fit, at most five segments. The current year and "All time" are always among them. As room allows, up to two more years join them, a later year first, then the years before the current one, all in date order.
- The other years are in a menu segment, "Earlier", or "Other years" when it holds a later year. Picking one shows that year in the segment.
- On very narrow screens the control has two segments: a menu of every year, showing the year chosen, else the current year, and "All time".
- Until a period is chosen in this browser, the current year is shown.
- The selected segment is shown by fill and check, not by bolder text, and every segment reserves room for its longest label, so the control never changes width when the selection changes.

## First run

0. The sign-in page, the site's own ([33](33-accounts-and-sign-in.md)): email and password, or "Continue with Google". A new user arrives through the invitation link the owner sent, which makes their account. Nothing else of the site opens before (U3).
1. Choose the data mode (Decided, [32](32-modes-and-sharing.md)): Standard (recommended, preselected), Private or Local, under the title "Sync mode" with "You can change it later in Settings". Standard shows the terms; declining them leads to Private or Local. Local shows a warning that the log can be lost. Built: Standard is preselected where the site offers it; choosing it, or Continue while it is selected, opens its terms in a dialog with "Accept and connect Google Drive" and "Not now" (which selects Private); Google's page follows, and the app opens once the first sync has the log's tables; the tracks follow in the background ([12](12-storage-and-sync.md), "Sync algorithm"). Where the site does not offer it, it shows "Not available on this site." and Private is preselected. Private then asks for the storage: Google Drive (preselected; works on phones too) or a directory on this computer (Chrome or Edge on a computer only), with a line on what each does, and a button: "Connect Google Drive" or "Choose a directory". A browser that already held a log before the modes existed is set to Local without asking.
2. Connect storage: in Standard, through the server (Google Drive first); in Private, Google Drive or a local folder (desktop Chromium only); Local needs none.
3. Google Drive: allow Touchdown to use its own folder (`drive.file`); the app creates the `Touchdown/` folder, or finds the one it created before and downloads the log from it. Later visits open from the browser's copy at once and sync in the background.
4. Offer import of existing data (the myFR24 export, any spreadsheet as CSV or `.xlsx`), and Getting started (below).

## Signing out

Decided: signing out removes the browser's copy of the log, once everything has synced. This keeps a log off a shared or borrowed computer.

- Google Drive or local folder: the app first checks that every change has reached the storage. Then it removes the log from this browser (both IndexedDB stores, the remembered view state) and signs out. A new sign-in downloads it again.
- Changes not synced yet (for example, sync waits for a Google sign-in): it says how many and asks; signing out anyway keeps the copy in this browser. (Built)
- Local mode: the browser holds the only copy, so signing out keeps it and says so. (Built; the export button is Proposed)
- In every mode, signing out also removes the app's offline copy, so the log no longer opens here without signing in ([30](30-architecture.md), "Offline"). The server ends the session, so signing out needs the network. (Built)
- Built in Settings → Account ([33](33-accounts-and-sign-in.md)). Each account has its own copy in the browser, so a kept copy is never shown to someone else signing in here.

## Opening

Decided: a loading screen shows from the first moment until the first page is ready.

- The name, one progress bar and one line saying what is being done, centred a third of the way down the screen.
- The progress bar is a final approach seen from the side: a Boeing 747, gear down, follows a dashed glide path down to a runway, and the path behind it turns gold. 0% is the start of the approach, 100% is touchdown.
- One bar from 0 to 100%. Before the app's code runs, the page's own bar creeps on, slowing, about a third of the way ("Loading the app…"). The app carries the same bar on from where it is as each step finishes, and the line names the step. The aircraft never jumps from point to point: it flies smoothly towards each step's progress, keeps creeping slowly between steps, never goes back, and lands once the first page is ready:

  | Step | Line |
  |---|---|
  | Reading the log and the reference data (at the same time) | "Reading your log and the reference data…", then whichever is still going: "Reading your log…" or "Loading airports, airlines and aircraft types…" |
  | Putting the rows in memory | "Preparing 2,740 records…" (the real count) |
  | Only while this browser's copy lacks the log's tables (a new browser, or a first download cut short by a reload): reading them from the storage | "Reading your log from Google Drive…" (or the folder's name); the bar creeps on |
  | First page ready | "Ready": the aircraft touches down and raises its nose. The runway turns gold and runs out to both edges of the screen, and the screen opens along it over the page, which has rendered underneath: the top half lifts away and the bottom half drops. With reduced motion the screen goes at once. |

- The tracks are read after the page shows; the masthead's sync state reads "Tracks 12 of 300" meanwhile, and Settings says the same. Tracks not read yet are counted in the masthead's tooltip and Settings ("4 recorded tracks are not in this browser yet"); such a flight's map draws the great circle and says its track is not here yet.
- While tracks are being read (the app's sync, or a share link's requests for them), each map and globe with flights still waiting for theirs says so in its top corner: "Loading tracks · 29 of 41", counting that map's own flights with a recorded track, or "Loading the recorded track" on a flight's page. It shows only after 400ms of loading, so a quick read never flashes it, and fades out when the last one is in. Meanwhile the great circles waiting for a track are drawn fainter, so a line about to be replaced does not read as the way the flight went (`lib/trackLoading.tsx`).
- When the log's tables cannot be read (sign-in needed, offline, the storage cannot be reached), the page shows what the browser has, and says the log has not been read yet instead of showing the empty log ([12](12-storage-and-sync.md), "Sync algorithm").
- A second tab opens from the browser's copy and shows the same log as the first ([12](12-storage-and-sync.md), "Tabs").
- Development only, loading the local backup (an empty browser, or a hard refresh): "Downloading the local backup…", "Reading the backup…", "Saving … records in this browser…", then the log is read again on the same bar. The page does not reload, so the bar runs once. A reload with the browser's cache turned off (DevTools' "Disable cache") is not taken for a hard refresh.
- Reduced motion: no creeping, gliding, flaring or fading; the aircraft jumps from step to step.
- If the log cannot be opened, the same screen shows the reason.
- A share link opens on the same screen (`share.html`, `src/share/main.tsx`): "Opening the link…" while the page's code loads and the link's content is read, "Loading airports, airlines and aircraft types…", then "Loading recorded tracks · 12 of 41" for at most 3 seconds more (the tracks are read from the moment the content is in, alongside the reference data), "Preparing the pages…", then it lands and the screen opens along the runway over the link's first page. A link that does not open opens the same way on its message.
- A recorded track that arrives after a map is showing (on a link, or from the app's sync) fades in over 400ms while the great circle it replaces fades out, on the flat maps and the globes. When a flat map's framing changes to take the track in, the map moves and zooms to the new view over 450ms, and its height follows, instead of jumping. A track there when the map first draws does not move, and changing the period redraws the map at once.

## Home

- Flights summary tiles: flights, distance, time, airports, airlines, aircraft.
- Sightings summary tiles: aircraft, sightings, airlines, families, type codes, special-livery aircraft.
- Most frequent airline / family / type for each.
- Coming up: the next planned flights (see Planned flights).
- Recent activity: last 5 flights, last sighting session.
- Stamps: the latest earned, with All stamps (see Stamps).
- Open issues count, with a link to Issues.

## Flights

**Figures (Decided, built).** Above the map, the period's figures as tiles, as on Home: flights and their distance, time in the air, the longest flight, the most flown route and the most flown airline. Pointing at the longest flight or the route shows it on the map. Home keeps its summary sentence.

**List.** Table with date, flight number, route, airline, type, registration, distance, duration, and a track icon (recorded track or great circle only; hovering it explains which, the source, and whether the track has gaps). A flight with no number (a private flight) is named by its registration there, in the flight page's header and pager, on maps' tooltips, on the Issues page and wherever else a flight is named by its number (`flightName` in core). Its flight number field stays empty. Filters by year, airline, airport, type. Search by flight number, airport or city, registration, airline or type (its code or name), as every search reads text ("Searching"), or by route: "SHA-PEK" (or "SHA PEK", "Shanghai - Beijing") finds it either way, "SHA > PEK" (or "SHA to PEK") one way. A code names only its airport, so "SHA" is not Pudong. The map above keeps the whole period in its frame while searching or filtering: the flights left out turn grey. `touchdown flights --search` reads it the same way (`packages/core/src/view/search.ts`). Beside the filters, when some flights have no recorded track: "N without a track (CSV)", the short list to send to someone who can find them ([23](23-tracks-and-maps.md), "Helping each other").

**Detail.** The heading sets the two airports in columns of one width, so the arc between them, and the time in the air and the distance under it, sit in the page's middle whatever the airports' names (on a phone the time and the distance each have a line of their own). Map or globe (track or great circle; see Globe), the times strip (boarding, takeoff, landing, time in the air, distance and route extension: the distance is the one flown along the recorded track when there is one, over the great circle, and a "?" beside a distance or a route extension that is a minimum says why; [23](23-tracks-and-maps.md), "Distance"), all fields, the linked airframe with its other flights and sightings, findings for this record. Beside Edit and Delete: Add track, or, once the flight has one, a Track menu (Download as KML, Replace with a track file, Remove the track). A chosen file is checked against the flight and shown above the map with what it holds, or why it cannot be used, until the user saves it or cancels; saving or removing is an import the Import page's history can undo ([23](23-tracks-and-maps.md), "Sources").

**Special livery (Decided, built).** A flight on an aircraft in a special livery says so in its lead sentence ("on D-AXYZ, an Airbus A350-900 in its Centenary livery"), and a band between the sentence and the map gives the aircraft the stage: its reference photo beside the livery's name, the registration, type and airline, how many of the user's flights on it were in that livery and when it was photographed in it. The aircraft card below then leaves the photo out. The aircraft's page has the same band under its sentence, in place of the side photo, and its timeline shades the records in the livery and names it. A livery typed as "Centenary", "centenary" or "Centenary Livery" is one livery (`sameLivery` and `liveryName` in `packages/core/src/livery.ts`). The photo is the registration's latest on planespotters.net, which may show a later livery.

**Quick add (requirement F3).**
1. Enter flight number and date.
2. Enter airports (autocomplete on IATA, ICAO, city, name). The web app looks no flight up: a flight lookup that would prefill airline, airports, times, type and registration works only for flights in the last 10 days with an AeroAPI key, or during the flight, and is not scheduled ([13](13-reference-data.md), "Flight lookups"; [40](40-roadmap.md), "Later").
3. Optional fields are collapsed under "More": seat, class, times, gate, livery, notes.
4. Every time field is a date-and-time input. A time at an airport Touchdown does not know cannot be stored with its UTC offset: its hint turns to the alert colour, "Not saved until XFRM is added as an airport", and the airport field offers to add it. The date part starts as the scheduled date (for landing: the date implied by the duration) and is always shown next to the time, so a takeoff after midnight is entered on the next day, not on the scheduled date.
5. Checks run as fields change; findings show inline.

## Planned flights

Decided (F5), built. A flight can be added before it is flown, from a booking say, and is planned until the user confirms it. Its status comes from the clock ([10](10-domain-model.md), "A flight's status"): upcoming until its time has passed, then due (counted, not confirmed), then flown once confirmed. Every time is shown at its airport, as everywhere in the app, so a flight reads the same in any time zone.

**Adding.** The Add flight form takes a flight still to come. Saved with its departure still to come at the departure airport, it is planned. There is no switch: its date or time says so. The times row asks for what is known by then, each at its airport's local time and stored with its UTC offset, as every time field is:
- A day to come at the departure airport: Boarding, Departure and Arrival, the ticket's scheduled gate times (`departureScheduledAt`, `arrivalScheduledAt`).
- Today there: those and Takeoff and Landing, until a departure still to come makes the flight planned, which puts Takeoff and Landing away.
- A day gone: Boarding, Takeoff and Landing, and the scheduled Departure and Arrival under More.

While the flight is still to come, a line above the times says so: "Still to come, so it is saved as a planned flight. Takeoff and landing are added once the flight has flown." A date to come is no fault ([20](20-validation.md), V-DATE-SANE).

**While it is upcoming.**
- Home: "Coming up" between the figures and the map, the next three upcoming flights, soonest first, whatever the period: the day and the departure time at the departure airport ("Sat 14 Dec, 09:40"), the flight number and the route, each opening its flight. Not shown when there are none.
- Home's and Flights' maps draw it dashed when its date is in the period ([23](23-tracks-and-maps.md), "Maps in the app").
- Flights lists it in its month, marked "Planned", and leaves it out of the month's totals and the figures.
- Its page: "Planned" after its date, the sentence in the future ("You plan to fly from London to New York"), the scheduled departure and arrival in the times strip, each at its airport, the dashed great circle. No Add track: a flight has no track before it flies.
- It is not counted anywhere ([24](24-statistics.md)).

**When its time has passed.** The flight is due. It counts, and is drawn and listed as a flown flight, marked "To confirm" in Flights on the owner's pages. Its page in the owner's app says "You planned to fly from London to New York" until it is confirmed. The app notices the moment without a reload or a sync.

**The reminder.** A note bar under the masthead, on every page of the owner's app, for the due flights whose reminder time (`remindAt`) has come, or that have none:
- One flight: "XY123 to New York was due to land at 18:05 New York time on Sunday 15 December. Confirm it, or update it with the aircraft, the times and your seat." The time is the arrival's at the arrival airport, as the ticket gives it. Without an arrival time, the departure's at the departure airport ("was due to leave London at 09:40"). With only a date, "was planned for Sunday 15 December".
- Several: "The times of 3 planned flights have passed. Confirm them, or update them with what happened."
- Its buttons: Confirm and Update for one flight (Update opens its edit form), Review for several (the first one's page), and "Remind me later", a menu: In an hour, Tomorrow, In 3 days, In a week. Its choice sets `remindAt` on each flight the bar names. It syncs, so every device waits, and the bar comes back at that time.
- The flight's page shows the same in a band above the map, whatever the reminder time: Confirm, Update, "Remind me later", and "If you did not fly it, delete it" beside Delete.

**Confirming.** A flight stops being planned:
- With Confirm, in the bar or on its page. One edit, undone as any edit is.
- When its edit form is saved once its time has passed: the user updated it. Saving the form marks a flight planned exactly when its departure is still to come, so a flight moved to a later day stays planned, and one moved into the past is flown.
- When an import matches it once its time has passed ([21](21-import-export.md), "Import pipeline").
- With `touchdown edit REF --clear planned` ([34](34-command-line.md)).

A flight that did not happen is deleted, as any flight.

**Elsewhere.**
- Share links show planned flights as the app does, without the reminder, the band or "To confirm" ([32](32-modes-and-sharing.md), "What a link shows").
- Left out until confirmed: the myFR24 export ([21](21-import-export.md), "Exports"), the track backfill and the list of flights without a track ([23](23-tracks-and-maps.md), "Backfill"), and the agent check of records in the log ([22](22-agent-verification.md), "Records in the log").
- The command line marks them in its lists and counts as the app does ([34](34-command-line.md), "Reading").

## Sightings

**Figures (Decided, built).** Above the map, six tiles: the aircraft photographed (and how many are new to the log), the days out and their airports, the most spotted airline and type, the special liveries, and the busiest day.

**List.** Table with date, location, registration, operator, type, special livery, phase (every phase it was seen in, one per line). Same filters and search as flights. A row opens the aircraft's page, as every list of aircraft does; a sighting not yet matched to an aircraft opens the sighting itself. A sighting is edited from the aircraft page's timeline.

**Quick add (single).** Registration, then date and location (default: last used), then phase (one tap; tap more for every phase it was seen in). After the registration is entered, the app shows what it knows about the airframe (type, operator, previous sightings, "you flew on this aircraft on ..."). When the log has the aircraft in a special livery, it asks whether the aircraft still wore it (Q-SPOT-LIVERY); session add asks the same on each row.

**Session add (bulk).** For a spotting session with many aircraft: set date and location once, then add registrations one after another (type or paste a list). Each row resolves in the background; rows with findings are marked. A single session can have more than 100 sightings, so this flow matters.

**Photo link.** Optional field: paste a Google Photos share link. Shown as a plain link. (Google offers no way to embed or resolve these links.)

**Photos (Proposed, [25](25-photos.md), "Viewing").** The user's own photos, when they add some: on a sighting's page, as a thumbnail in the list, and full screen with the next and previous photos of the record. A record without photos shows planespotters.net's photo as today. They replace the Google Photos link once built; a link to a photo kept elsewhere stays a link.

## Aircraft

**Figures (Decided, built).** Above the list: the aircraft in the log (all confirmed, or how many have no serial number yet, for the owner only), those flown on and how many of them were also photographed, those photographed, those in a special livery, and the aircraft flown on most.

**List.** Distinct airframes with type, current registration, operator, number of flights, number of sightings, first and last seen. An aircraft in a special livery has a capsule after its registration for each livery, named as on its page. Filters: all, flown on, flown and photographed, and special livery (a flight or sighting in one).

**Detail.** Facts (MSN, first flight, type, model), registration history, operator history, timeline of the user's flights and sightings, special liveries seen. An aircraft with a special livery in the log gets the livery band under its sentence (see Flights, "Special livery"). With the user's own photos of it (Proposed, [25](25-photos.md)), they show newest first, the first one as its picture in place of planespotters.net's.

**Tools.** Merge airframes, split a registration period, set MSN, edit facts (stored as user values, see `field_provenance`). See [11](11-aircraft-identity.md).

**Facts and their sources.** Each fact says where it came from: "from OpenSky", "from Flightradar24" (linked to the page), "from your sheet", "entered by you". "Look it up" links open airfleets.net, aviation.flights, planespotters.net and Flightradar24 with the registration filled in. "Paste from a web page" reads the serial number, line number, first flight and delivery dates from text copied off one of those pages, shows what it found and warns when the page cannot be about this aircraft (it first flew after one of the user's records); "Save these" stores the values as the user's. See [13](13-reference-data.md), "Airframe facts".

## Aircraft types

Decided, built (`pages/Types.tsx`, `TypeManufacturer.tsx`, `TypeFamily.tsx`, `TypePage.tsx`, `TypeCompare.tsx`, `lib/typeEntries.ts`): "Aircraft types" in the More menu, beside Import, Issues, Shared links, Settings and Getting started. Not on a share link's pages. The figures and drawings are [13](13-reference-data.md), "Type figures" and "Silhouettes".

- **The list** (`/types`): a sentence of how many type codes and families there are and how many of these types the log has flown on and photographed. Search by name, manufacturer, family or code ("Searching"), Manufacturers (to start with) or List, a role (airliners, business aircraft, light aircraft, helicopters, military, other), "All" (to start with) or "In your log", and Compare. Every ICAO type code from the reference data: a curated family of more than one type as one row, every other type as its own. A family of one type (the Concorde, the A380) is its type here and on every types page: its row is the type's, leading to the type's page, it counts as a type and not a family, and the type's page shows no family. The families stay in the reference data, so Statistics groups by them as before. A search also lists the types of a family it names, each in a row of its own above its family's, the more precise answer first, leading to the type's page: "748" finds the 747-8, then the Boeing 747, "A320neo" the three neos, then the A320 family. A search for the family's own name ("747") finds the family alone, but for a code typed whole ("A320" lists the A320, then the family). Not ICAO's codes for a group of aircraft without a designator of their own (ZZZZ, GLID, BALL, GYRO, PARA, SHIP, UHEL, ULAC), which have no manufacturer: they have no page, and an aircraft's page does not link one. Manufacturers shows the best-known manufacturers of the role chosen as cards, in alphabetical order: for every role and for airliners, the airliners' (Aérospatiale-BAC, Airbus, Boeing, Bombardier, COMAC, Embraer, Ilyushin, Lockheed, McDonnell Douglas and Tupolev), for business aircraft Beechcraft, Bombardier, Cessna, Daher, Dassault, Embraer, Gulfstream, Hawker Beechcraft, Honda and Pilatus, for light aircraft Beechcraft, Cessna, Cirrus, De Havilland Canada, Diamond, Mooney, Pilatus, Piper, Quest and Tecnam, for helicopters AgustaWestland, Airbus Helicopters, Bell, Bell-Boeing, Boeing Vertol, Kamov, Leonardo, Mil, Robinson and Sikorsky, for military aircraft Airbus, Boeing, Dassault, Embraer, Fairchild, Lockheed, Northrop, Northrop Grumman, Saab and Tupolev, chosen among those with types drawn with their family's shape or their own (`POPULAR_MAKERS` in core). The factory stamps follow the list for every role ([24](24-statistics.md), "Factory airfields"). Each card has up to three of its types of the role drawn in the room of three at the card's left (one or two in its middle), the same whatever the log has: chosen ones for Airbus (A320, A330-300, A380), Boeing (747-400, 757-200, 767-300), Embraer (E175, ERJ 145, E195), Ilyushin (Il-14, Il-62, Il-96), Lockheed (SR-71, L-1011, C-5), McDonnell Douglas (DC-8, DC-9, DC-10) and Tupolev (Tu-144, Tu-154, Tu-204), else its types with the most codes, a family by its first type with figures, else by its first of the role (a chosen type the filters leave out gives its place to the next), only types drawn with their family's shape or their own, as the usual shape of its kind may put a type's engines in the wrong place. A manufacturer the filters leave nothing to draw of has no card, and with no cards there is no such section: other aircraft have none, too few of them being drawn so. Then every manufacturer from A to Z under a row of letters; each leads to the manufacturer's page. List, or any search, shows a heading per manufacturer (leading to its page) and a row per family or type, by name as on a manufacturer's page: its silhouette in a square, larger the larger the aircraft, its name and codes (by generation, then model), its length and seats from the smallest type to the largest, and its flights and sightings in the log; 200 rows at first, 200 more as the end comes into view (or "Show more types"). A family's row opens the family's page, a type's row the type's page.
- **A manufacturer** (`/types/manufacturers/boeing`, `pages/TypeManufacturer.tsx`): its name, a sentence of how many types and families it has and what the log has of them, its roles as chips when it has more than one, then its families and types by name, numbers in order (the 717 before the 727, the C-17 before the C-135), so a type without a family sits beside the family it is a variant of, each with the year it first flew (a family's from its article, a type's from Wikidata). A row without a length or seats says what the reference data has of its engines ("1 piston engine"). The silhouette column goes when none of its types has a drawing (a glider maker's, whose types Wikidata gives no figures for), and the log's columns when the log has none of its types.
- **A family** (`/types/families/boeing-737`, `pages/TypeFamily.tsx`, its name's slug as a manufacturer's is): its name and manufacturer (leading to the manufacturer's page), a sentence of how many type codes it has, when the first flew and what the log has of them; its codes side by side as on a type's page (`components/TypeFamilyTable.tsx`), without differences; its history from its article; the log's aircraft of its types; and where the history comes from, each type's page saying where its figures and drawing come from. A family of one type has no page: its address (`/types/families/concorde`) opens the type's page in its place, and a chat app's preview of it is the type's.
- **A type** (`/types/A21N`): its name and code, its family (none for a family of one type), Compare; a sentence of its length, span and maximum take-off weight and what the log has of it; the type drawn from above as a measured drawing on a tonal panel, its span marked across the top, its length down the side (each only where the type's own figures give it), with a scale bar, and over it, for a type with moving parts, a small segmented button for how they show ("Moving parts" below); its figures; its family's codes side by side under the family's name (leading to its page), by generation, then model (every code, one without figures with dashes), each drawn to one scale with its figures and, where it differs, the difference from this type's ("+6.94 m"), its engines and its flights and sightings; the family's history (first flight, entry into service, number built, status), a family of one type's included, or a type without a family's own from Wikidata; the log's aircraft of the type; and where the figures and drawing come from, linked to the Wikipedia article's revision and, where they give any of them, the Wikidata item's and the type's own article's, the type of its family whose fuselage width it shows or the comparison article that gives it ([13](13-reference-data.md), "Type figures"), and whether the drawing is checked or the usual shape of its kind. The type on an aircraft's page leads here. Each figure, here, in the family's table and on Compare, a difference included, shows the same in other units in the tooltip, on hover or a tap: a length in feet and inches, a weight in kilograms and pounds, a range in kilometres and miles, a speed in km/h and mph, a wing area in square feet (`components/Measured.tsx`).

- **Open to anyone** (Decided, built: `apps/web/types.html`, `src/types/`, `vite.types.config.ts`, [33](33-accounts-and-sign-in.md), "Pages anyone can open"). - **Moving parts** (Decided, built: `lib/motion.ts` `useTypeMotion`, DESIGN.md "Motion"). The parts move to the pose chosen, and a page opened in one shows it at once. Held folded or swept, the span is marked as its source gives it with the wings so ("Span 64.84 m folded", "Span 35.6 m swept"), its line moving with the tips. - **Previews** (Decided, built: `apps/web/scripts/type-previews.ts`, `packages/server/src/types.ts`, `compare.ts`). A types page's address pasted into a chat app shows a preview, as a share link's does ([32](32-modes-and-sharing.md), "Previews"): a title, a line under it and a picture.

It is drawn without a canvas or a library (`raster.ts`): each polygon's cover of the pixels it crosses, and a PNG of 256 palette colours compressed with deflate's fixed codes. It takes about 2 ms, up to about 8 ms on its first request to a Worker. Its address carries a hash of the two types' pictures' (`?v=`) and of how it is drawn (`DRAWN` in `compare.ts`), so it changes when either drawing does. A code without a drawing gets 404.
  - The server puts them in the page's head as Open Graph tags and as its title, in place of the file's own, with `Vary: Accept-Language`. A picture's address carries a hash of it (`?v=`), so it is cached for a day. An address with no preview (a code without a page) keeps the file's own, "Aircraft types · Touchdown". Each page then keeps the browser's title its own as the reader moves between them (`lib/title.ts`): the list's, Compare's and each type's, manufacturer's and family's name, as the server gives its address, and the app's name, "Touchdown", on a page without one, so a page's title never stays after it is left.

## Airports

**Opened from** any map: clicking an airport dot, an airport label or a spotting location on the flat maps (Home, Flights, Spotting, an airport page) or on a globe opens `/airports/<id>`. On a flight page, the airport names in the header and the airports on the map link there too. Hovering an airport shows its name and the number of flights in the period.

**Page.** Follows the shared period control.
- Header: the airport code, city, full name, country, ICAO code.
- Lead sentence and facts: departures, transits, landings, the airport flown with most often, aircraft photographed (sightings and days), the first day the user was there.
- A transit is a landing at the airport followed by the user's next flight leaving it within 24 hours (the next day at most when times are missing). Its two flights count as one transit, not as a landing and a departure.
- Map or globe (see Globe) of the flights to and from the airport and the spotting dot; other airports on it open their own pages.
- Flights list, newest first, 20 per page, with a "Transit" pill on both legs of a transit.
- Aircraft photographed there, one row per airframe (times seen there, flights on it, last seen there), 30 per page.
- An airport the user added says so under the header ("An airport you added"), with "Edit", which opens the airport's form.

**Airports of your own** (Decided, built). An airport field (a flight's From and To, a sighting's and a spotting session's location) suggests airports by code, place and name. A code or a name the airports shipped with the app do not have loads the small airfields first ([13](13-reference-data.md), "Airports"). Still unknown, the hint under the field reads "Not a known airport code" with "Add as an airport…". On the Issues page, an unknown airport code has "Add EGLM as an airport…". Both open a dialog (the share dialog's card, 36rem wide):

- Code: what the record has, when it is three or four letters or digits. A code the app knows already is refused, naming the airport.
- Name, town or city.
- Position: latitude and longitude as a map gives them, in decimal degrees or degrees, minutes and seconds, with or without N, S, E and W (`parsePosition`). Under it, how far the nearest known airport is, so a wrong position shows.
- Country and time zone: set from the nearest known airport until the user chooses them, saying which airport gave the zone.

Saving links every flight and sighting that has the code, or what the field held, and no known airport, and says how many. A flight's times at it are stored with its UTC offset from then on. The airport is in the log (`airport_overrides`, [10](10-domain-model.md)), so it syncs and share links show it.

## Addresses

Pages of records have readable addresses made from what the record is, not from stored ids, so an address still works after the log is rebuilt from its sources (Decided).

| Page | Address | Made from |
|------|---------|-----------|
| Flight | `/flights/2025-03-14T0830-LHR-CDG` | Local takeoff date and time at the departure airport, then departure and arrival codes. Without a takeoff time: `/flights/2025-03-14-LHR-CDG-XY300` (flight day, route, flight number if any). |
| Sighting | `/spotting/2025-03-14-AMS-N1001X/edit` | Day, place, registration: one sighting per aircraft, place and day (Q-SIGHTING-UNIT). |
| Aircraft | `/aircraft/airbus-a320-99001`, `/aircraft/boeing-28470` | Maker and serial number, the airframe's identity ([11](11-aircraft-identity.md)), with the series for Airbus, which numbers each family from 1. Until the serial number is known: `/aircraft/N1001X-2024-03-01`, the registration it was first seen with and that day (what the provisional identity is made of). |
| Airport | `/airports/LHR` | IATA code, or ICAO when the IATA code belongs to another airport too. |
| Shared link | `/p/<id>`; pages inside a whole-log link follow a `#` | A random id, not made from the record ([32](32-modes-and-sharing.md)). |

- Neither the flight number nor the registration is the key. Flight numbers repeat (an airline often uses one number both ways, or for a shuttle flown several times a day); no one leaves the same airport twice in one minute, so the takeoff time is. Registrations rotate when an aircraft changes hands and are reused on other aircraft; the serial number stays with the airframe.
- A sighting keeps its registration in the address: it records one moment, and the registration at that moment does not change.
- If two records would get the same address, the later one gets `-2`, `-3`.
- Addresses ignore case. Old addresses still open their page: one made from a stored id, and an aircraft address made from a registration (bare, or with the day first seen) when only one aircraft in the log carried that registration. So an aircraft's address changes when its serial number becomes known, and the old one keeps working. An Airbus address also changes when its type becomes known, which gives its series; the old one does not stay.
- Editing a flight's takeoff time or route, or a sighting's day, place or registration, changes its address.

## Searching

Decided, built (`searchFold`, `searchText` and `searchMatcher` in `packages/core/src/view/search.ts`). Every search reads its text one way: the Flights, Spotting and Aircraft lists, the types list, Compare's pickers, the form fields that suggest airports and airlines, and the CLI's `--search`.

- **Only letters and digits count**, in lower case and without accents: "Tu160", "TU 160" and "Tu-160" are the same search, and so are "São Paulo" and "sao paulo", "G-ABCD" and "gabcd". Any dash counts as one, the en dash and the non-breaking hyphen included.
- **Words in any order.** A thing is found when it holds each word of the search, each within one of its fields (a word never runs from the end of one field into the next): "boeing 300er" finds the 777-300ER, "160 tupolev" the Tu-160, "London New York" the flights between them either way. A route one way ("SHA > PEK", "SHA to PEK") is read as the route, not as its words.
- **A type by every name it goes by**: its ICAO code, its name with its maker, its family's name and code ("B777" finds every 777), and the titles of the articles its figures come from (Wikipedia's and Wikidata's), so "777X" finds the 777-8 and 777-9 and "Dreamliner" the 787s. The Flights list finds a flight by its type's name as well as its code ("A350", "777").

## Going back

Decided: Back shows a page as it was left. Forward does the same.

- Kept: the search text, filters and chips, sort, tab, page number, the custom view's choices and the figure picked in it, map layers, expanded sessions, every "Show all" (Statistics' lists and tables, the custom view's rows), how many rows a list that grows as it scrolls has loaded, and the scroll position. On every page that has them, the types pages included: the list's search, Manufacturers or List, the role and "In your log", and a manufacturer's role chips, so Back from a type shows the role chosen.
- Built with `useViewState` (`lib/viewState.ts`) in place of React's own state, for each of these choices.
- Kept per visit (each browser history entry), not per page. Opening a page from the navigation starts it fresh; going back to an earlier visit shows that visit as it was.
- A page's link back to the page it belongs under (the crumb: "Aircraft types" on a type's, a manufacturer's, a family's and Compare's page, "All flights" on a flight's, "All aircraft" on an aircraft's, "Spotting" on a sighting's form and the spotting session, a flight form's link back and its Cancel, and the shared log's sighting page) goes back to that page's visit when the page was opened from it, through pages beneath it only (the list, a manufacturer, one of its types), as Back would, so it shows as it was left. Opened from anywhere else, it opens that page fresh, as a link does. Built with `BackLink` (`lib/back.tsx`), which keeps which visit each visit was opened from, in the tab's session storage. An airport's Back button goes back while there is a page of the app to go back to, else to Statistics.
- Checked, not left to be noticed:
  - `npm run check-back -w @touchdown/web` (`apps/web/scripts/check-back.ts`), against the dev server: on every page that is not a form, it changes each control the page offers (choices, tabs, selects, checkboxes, toggles, "Show all", a list's pages, the search) and scrolls, follows a link to another page, comes back with Back and with the other page's link back, and reports anything not as it was left. Each page is checked only scrolled, with every control changed on each of its tabs, and with only the search.
  - It finds a control by its role and state (`aria-checked`, `aria-selected`, `aria-pressed`, `aria-expanded`, `aria-current`), so every control that changes what a page shows carries them: a "Show all" is a disclosure with `aria-expanded`. A control that is a setting shared by every page, not the page's view, is marked `data-setting` and left alone (the period).
  - The web app's tests (`lib/back.test.ts`) fail when a crumb links back with a plain `Link` instead of `BackLink`, or a "Show all" lacks `aria-expanded`.
- A reload keeps them. They are held in the browser's session storage for the tab and never leave the browser.
- A kept choice that is no longer one of the page's (a tab, a chip or a sort renamed or removed since it was kept) is read as the page's default, so a reload after an update never shows a page with no tab chosen and nothing under it. Each `useViewState` with a fixed set of values is given that set.
- The period (year) is not part of this: it is one setting shared by every page (Period control).

A wheel's or a trackpad's zoom eases in and out over about 200ms, like a critically damped spring, so the notches of a turning wheel run together without stopping between them. From 0.3 of the stage's shorter side to 40 times the view that fits the routes (`lib/globeZoom.ts`).

- Pointing at a route or an airport describes it; clicking opens its page. With a finger, a first tap describes it, and a second tap, or a tap on its tooltip, opens it (see Touch). Clicking the globe itself never scrolls the page.
- Framing: the globe turns to the routes it shows and zooms in on them, but never so far that its edge leaves the view.

## Touch

Decided, built: a finger reaches what a mouse's hover shows, and the page still scrolls under it.

- A flight's map and globe: a finger that lands on the recorded track follows it, the aircraft and its state going with the finger (the nearest position within 64px) until it lifts, and the page does not scroll under it. A tap shows the nearest position within 28px. Anywhere else on the flat map a finger scrolls the page; on the globe it turns it.
- Routes, spotting places and airports on the maps and globes: a first tap shows the tooltip a mouse's hover shows, a route highlighted too, and a second tap on the same opens its page. So does a tap on the tooltip, a larger target than a route's line, which a chevron at its end marks. On the flat map a finger's tap takes the route whose line is nearest where the finger touched, if it is within 10px. The map measures this itself, as a phone's browser would move a tap onto a line's target from anywhere in the rectangle round it. A place under the finger comes first. A mouse's target along a route is 12px wide, and a place's at least 24px across.
- Charts (Home's months, a flight's altitude): a tap shows the month's or the moment's figures, and a finger sliding sideways along the chart moves through them. A vertical swipe scrolls the page.
- What a tap shows stays after the finger lifts and goes when a finger touches elsewhere. The tooltip sits above the finger and centred on it, where the hand does not cover it.
- A help tip ("?"): a second tap, or a tap elsewhere, closes it.
- A list of suggestions (airports, airlines, places) picks one when the finger lifts on it without moving, so the list scrolls under a finger without picking.
- Looks that only hover gives are left out where there is no hover: a lead sentence's phrase let go does not look held. A figure with other units has a faint dotted underline, to say a tap shows them.
- Words a mouse reads in a tooltip show on a phone too, a phone showing no `title` (`components/HelpTip.tsx`). The notes of a flight map's legend, with where its track comes from, the altitude chart's source and a share link's track status show on a tap, marked by a faint dotted underline where there is no hover. A control whose title says what it does (the flights without a track as CSV, Add track) has a "?" beside it there. The counts beside a type's aircraft are written beside their dots, a ranked list's label shows whole, and an airport's aircraft seen on fewer days than times has the days under its count.

## Import

Wizard: choose source → upload or pick file → column mapping (auto-detected for known formats) → review → commit.

Review screen:
- Airports in the file that Touchdown does not know, named in a line above the rows with "Add … as an airport…" for each (the airport dialog, see Airports). Their flights' times are left out until then; once one is added, the file is read again ([21](21-import-export.md), "Building date-times from clock times").
- One row per record: parsed values, normalised values, resolved airframe.
- Findings from the deterministic checks.
- Agent suggestions if a check result was loaded ([22](22-agent-verification.md)).
- Per row: accept, edit, or skip. Per suggestion: accept or reject. Bulk accept by rule.
- Commit creates an ImportBatch. Import history lists batches with an undo button.

**Check with an agent** (Decided, built). A panel under the summary, above the row filters:
1. "Save the request" saves `touchdown-check-<id>.json` to the browser's downloads.
2. The command to run in a terminal in the Touchdown directory (the user's copy of the repository), with a copy button: `./touchdown check ~/Downloads/touchdown-check-<id>.json`. The agent, its rules and whether notes are sent are the CLI's settings on that computer ([22](22-agent-verification.md)). Before the steps, a note says what the Touchdown directory is and how to set it up once (`git clone`, `npm install`, an agent signed in and chosen with `./touchdown agent`), with a link to the README's "Set up".
3. "Load the result" reads the `.result.json` the command writes next to the request.
- Under the steps, a line says what is sent and what never is.
- Once a result is loaded, the panel says how many rows were checked and how many suggestions there are, how many are used or dismissed, and how many answers did not pass Touchdown's checks or got no answer. Buttons: use every high-confidence suggestion, show those rows, load another result, remove the check.
- An "Agent" filter shows the rows with suggestions; "Need a look" includes rows with suggestions not yet used or dismissed.
- Each suggestion sits under its row's findings: the field, the current value struck through, the suggested value, the reason, the confidence and where it comes from (the reference data, your other rows, what the agent knows). Use or Dismiss, and Undo after either. A row the agent doubts without a suggestion shows its note.
- Using a suggestion updates the row at once: its status, its findings and the summary are worked out again with the new value. In "Disagrees", a field the agent set is ticked and locked.
- A result from another file is refused. The same file chosen again (after a reload) takes the same result.

**Columns of a spreadsheet** (Decided, built). When the columns of a file are unclear, or rows cannot be read with what was worked out, a column step comes before the review: "The rows are: Aircraft you saw / Flights you took", then each column with three of its values and a select of what it holds ("Not used" included); unclear columns are shaded with the reason. "Read the rows" is enabled once the mapping can read rows (one column per field, a registration for sightings, a date and flight number or airports for flights). The layout is remembered in the browser; the review then says how the columns were read, with "Change the columns" ([21](21-import-export.md), "Source: any spreadsheet").

**The inbox waiting** (Decided, built). Files in the inbox of the user's storage (and, in development, `data/private/inbox/`) not imported yet, from `touchdown spot` and `touchdown add`, are listed above the file picker as "Waiting to be imported": the session's date and time (or "Added from the command line" and the time), how many flights and sightings are not in the log yet and which command made the file, Review and Discard. On every other page a note bar under the masthead says how many flights and sightings are waiting, with "Review and import" and "Not now" ([21](21-import-export.md), "Getting a session to the web app").

**An inbox file** (Decided, built). The file picker also takes the `.json` inbox file that `touchdown spot` or `touchdown add` writes ([21](21-import-export.md)). The review says the rows were filled and checked in a spotting session, and by which agent, or checked against the log by `touchdown add`. Beside Import, "Discard this file" deletes it from the inbox after a confirmation, and nothing goes into the log (built). The agent check panel is not shown. What the session left open shows as a warning on its row, and "Need a look" opens on those rows. A check request or result chosen here by mistake gets a message saying where it belongs.

**A change file** (Decided, built). A file from `touchdown edit`, `delete` or another changing command ([34](34-command-line.md), "Change files") opens on the Import page in its own review, from the list, the bar or the file picker: each change with what it is about, a note when it has nothing left to do or its record was changed since (left out unless ticked), and its values before and after; the findings the changes taken would bring; "Import N changes" and "Discard this file". The import is one batch in the history ("N changes made"), undone like any import. The waiting list and the bar count changes with the records ("1 change to make").

## Issues

Fields changed on two devices come first (Decided, built; [12](12-storage-and-sync.md), "Sync algorithm"): "Changed on two devices", one item per field, with the record it belongs to, the value in the log (and on which device and when it was made, or "changed since") and the other change. "Keep it" closes it; "Use the other" sets the other value. An entry deleted on one device and changed on another (or tagged, or given a photo link) reads "Deleted and changed", with "Keep the entry" and "Delete it". A value as typed and its normalised form are one item. What two devices made twice is settled without asking where nothing is lost ([12](12-storage-and-sync.md), "Settling what two devices made"); only what needs a choice is listed here. The choice syncs like an edit, so it closes on every device. Private values show as "(private)". They count in the lead sentence, the Open tab and the masthead's issues badge.

Then all open findings grouped by rule. Each has the records involved, the suggested fix, and "accept warning" (IssueAck). An unknown airport code has "Add … as an airport…" (see Airports). A second tab lists accepted warnings so they can be reopened.

Order (Decided, built): groups by severity (errors first), then in the fixed order of the rules in `packages/core/src/rules`; within a group, newest record first. The order does not depend on how many findings a group has, so accepting or fixing one brings the next into its place and the groups do not move.

## Language

Built (G12): every word the web app, the share and sign-in pages, the CLI and the server show is a message in `packages/i18n/messages/<language>/`, looked up by key (`packages/i18n/README.md`). UK English is the source. The web app, the share and sign-in pages, the CLI and the server are also in American English, German, Simplified Chinese and Traditional Chinese for Taiwan (`en-US`, `de-DE`, `zh-CN`, `zh-TW`, built).

| Part | Rule |
|------|------|
| Messages | A subset of ICU MessageFormat, the format translation tools read: named arguments, plural forms by the language's own rules, choices (`select`), and tags for bold text and links. One message for each whole sentence, never one put together from pieces, so a translator can change the word order (Decided). |
| Choosing the language | The first of the browser's languages the interface has in some form (Chinese of Hong Kong and Macao gets Traditional Chinese, English of Australia gets UK English), or a language chosen in Settings, which is kept in the log (`settings.language`) for every device, like the theme. It is put in place before the first page is drawn. Changing it reloads the page. A language chosen on another device is used from the next load, not by reloading a page in use. Each browser keeps a copy of the choice for the pages drawn before the log is open: the loading screen and the sign-in pages. Settings lists the languages by the names they give themselves. The share page uses the viewer's language, never the owner's: the language their own account chose when they are signed in to the site, else the one chosen in this browser, else the browser's languages. The CLI and the server follow the locale, not a setting: the CLI the system's (`LC_ALL`, `LC_MESSAGES`, `LANG`, `LANGUAGE`, as other command-line tools read it, [34](34-command-line.md), "Language"), the server each request's `Accept-Language` (Decided, built, Q-I18N). |
| Translations | German and Chinese address the user informally (du, 你). en-US has only the messages spelt differently, and the rest come from UK English. Chinese is set in Source Han Sans for its script (served with the app as Noto Sans SC and TC, the same type, loaded by the characters a page shows), with Latin letters and figures in Source Sans 3, and the system's Chinese face standing in until its files are in and offline. A label put inside a sentence is lower-cased only in English. Airports, the places they serve and airlines are shown by their names in the language where Wikidata has one, and the makers of aircraft types where the language has its own name for them ([13](13-reference-data.md), "Names in other languages"), else in English. Notes for each language and the words for Touchdown's terms: `packages/i18n/GLOSSARY.md` (Decided, built). |
| Numbers, months, weekdays, lists | In the chosen language, from the browser's formatting (Intl) (Decided). |
| Date format | A choice of its own, but its choices come from the language (Decided): the language's own way ("15 Mar 2025" in UK English, "2025年3月15日" in Chinese), the other regional ways of the same language where they differ ("Mar 15, 2025" for English), and ISO 8601 ("2025-03-15") in every language. Month and weekday names stay in the language. Kept in the log beside the language (`settings.dateFormat`), and used at once on every device: pages drawn after use it. A share link shows dates in the viewer's own choice. |
| Times | 24-hour in every language and date format, as aviation writes them (Decided). |
| Kept in English | The agent's prompts, file formats (CSV and spreadsheet headers, the myFR24 columns), the column names an import recognises, command names and flags (Decided). |
| The server | Its errors are messages too, answered in the request's language: the first of the `Accept-Language` header's languages the interface has, else UK English ([33](33-accounts-and-sign-in.md), "Server API"). |
