# 31 UI

Pages and the main flows. Layout details come later; this fixes what each page must do.

The app is responsive: every page works in Chrome on Android. iOS is not a target. It has light and dark themes (G10), and all copy uses UK English (G9), kept in message files so it can be translated (G12, "Language" below). The quick-add flows are designed for phone first, because sightings are often logged at the airport.

## Navigation

```
Home | Flights | Sightings | Aircraft | Statistics | Import | Issues | Settings
```

A page of the main navigation (Flights, Spotting, Aircraft, Statistics) shows its name as a title on a phone only, where the navigation is at the bottom of the screen. On a computer the navigation above names it, and the title is there for screen readers (Decided, built). Home opens with its summary sentence instead.

## Airport codes

The Settings "Codes" choice (IATA, ICAO or both) applies on every page (Decided). Every code shown as text follows it, both codes when the user chose both ("LHR/EGLL → CDG/LFPG" in flight rows, facts, links, tooltips, routes in Statistics). Large type (flight and airport headers, the latest flight on Home) shows one code, ICAO when the user chose ICAO, otherwise IATA, with the other code small beneath or beside it when the user chose both. Map labels show one code. An airport named in text carries its code in parentheses: "London Heathrow (LHR)". Addresses (`/airports/LHR`) always use IATA where it is unambiguous.

## Period control

Home, Flights and Statistics share one period control.

- Segmented buttons (outlined pill, equal-width segments, a check on the selected one) while they fit, at most five segments: the most recent years, then "All time".
- Older years move into an "Earlier" segment that opens a menu; picking one shows that year in the segment.
- On very narrow screens the control becomes a single menu button listing every period.
- The selected segment is shown by fill and check, not by bolder text, and every segment reserves room for its longest label, so the control never changes width when the selection changes.

## First run

0. The sign-in page, the site's own ([33](33-accounts-and-sign-in.md)): email and password, or "Continue with Google". A new user arrives through the invitation link the owner sent, which makes their account. Nothing else of the site opens before (U3).
1. Choose the data mode (Decided, [32](32-modes-and-sharing.md)): Standard (recommended, preselected), Private or Local, under the title "Sync mode" with "You can change it later in Settings". Standard shows the terms; declining them leads to Private or Local. Local shows a warning that the log can be lost. Built: Standard is preselected where the site offers it; choosing it, or Continue while it is selected, opens its terms in a dialog with "Accept and connect Google Drive" and "Not now" (which selects Private); Google's page follows, and the app opens once the first sync has the log's tables; the tracks follow in the background ([12](12-storage-and-sync.md), "Sync algorithm"). Where the site does not offer it, it shows "Not available on this site." and Private is preselected. Private then asks for the storage: Google Drive (preselected; works on phones too) or a directory on this computer (Chrome or Edge on a computer only), with a line on what each does, and a button: "Connect Google Drive" or "Choose a directory". A browser that already held a log before the modes existed is set to Local without asking.
2. Connect storage: in Standard, through the server (Google Drive first); in Private, Google Drive or a local folder (desktop Chromium only); Local needs none.
3. Google Drive: allow Touchdown to use its own folder (`drive.file`); the app creates the `Touchdown/` folder, or finds the one it created before and downloads the log from it. Later visits open from the browser's copy at once and sync in the background.
4. Offer import of existing data (FR24 CSV, Google Sheets, generic CSV), and Getting started (below).

## Signing out

Decided: signing out removes the browser's copy of the log, once everything has synced. This keeps a log off a shared or borrowed computer.

- Google Drive or local folder: the app first checks that every change has reached the storage. Then it removes the log from this browser (both IndexedDB stores, the remembered view state) and signs out. A new sign-in downloads it again.
- Changes not synced yet (for example, sync waits for a Google sign-in): it says how many and asks; signing out anyway keeps the copy in this browser. (Built)
- Local mode: the browser holds the only copy, so signing out keeps it and says so. (Built; the export button is Proposed)
- In every mode, signing out also removes the app's offline copy, so the log no longer opens here without signing in ([30](30-architecture.md), "Offline"). The server ends the session, so signing out needs the network. (Built)
- Built in Settings → Account ([33](33-accounts-and-sign-in.md)). Each account has its own copy in the browser, so a kept copy is never shown to someone else signing in here.

## Opening

Decided: a loading screen shows from the first moment until the first page is ready.

- The name, one progress bar and one line saying what is being done, centred a third of the way down the screen.
- The progress bar is a final approach seen from the side: a Boeing 747, gear down, follows a dashed glide path down to a runway, and the path behind it turns gold. 0% is the start of the approach, 100% is touchdown.
- One bar from 0 to 100%. Before the app's code runs, the page's own bar creeps towards 30% ("Loading the app…"). The app carries the same bar on as each step finishes, and the line names the step:

  | Step | Line |
  |---|---|
  | Reading the log and the reference data (at the same time) | "Reading your log and the reference data…", then whichever is still going: "Reading your log…" or "Loading airports, airlines and aircraft types…" |
  | Putting the rows in memory | "Preparing 2,740 records…" (the real count) |
  | Only while this browser's copy lacks the log's tables (a new browser, or a first download cut short by a reload): reading them from the storage | "Reading your log from Google Drive…" (or the folder's name); the bar creeps on |
  | First page ready | "Ready": the aircraft touches down and raises its nose, and the screen fades out over the page, which has rendered underneath |

- The tracks are read after the page shows; the masthead's sync state reads "Tracks 12 of 300" meanwhile, and Settings says the same. Tracks not read yet are counted in the masthead's tooltip and Settings ("4 recorded tracks are not in this browser yet"); such a flight's map draws the great circle and says its track is not here yet.
- While tracks are being read (the app's sync, or a share link's requests for them), each map and globe with flights still waiting for theirs says so in its top corner: "Loading tracks · 29 of 41", counting that map's own flights with a recorded track, or "Loading the recorded track" on a flight's page. It shows only after 400ms of loading, so a quick read never flashes it, and fades out when the last one is in. Meanwhile the great circles waiting for a track are drawn fainter, so a line about to be replaced does not read as the way the flight went (`lib/trackLoading.tsx`).
- When the log's tables cannot be read (sign-in needed, offline, the storage cannot be reached), the page shows what the browser has, and says the log has not been read yet instead of showing the empty log ([12](12-storage-and-sync.md), "Sync algorithm").
- A second tab opens from the browser's copy and shows the same log as the first ([12](12-storage-and-sync.md), "Tabs").
- Development only, loading the local backup (an empty browser, or a hard refresh): "Downloading the local backup…", "Reading the backup…", "Saving … records in this browser…", then the log is read again on the same bar. The page does not reload, so the bar runs once. A reload with the browser's cache turned off (DevTools' "Disable cache") is not taken for a hard refresh.
- Reduced motion: no creeping, gliding, flaring or fading; the aircraft jumps from step to step.
- If the log cannot be opened, the same screen shows the reason.
- A share link opens on the same screen (`share.html`, `src/share/main.tsx`): "Opening the link…" while the page's code loads and the link's content is read, "Loading airports, airlines and aircraft types…", then "Loading recorded tracks · 12 of 41" for at most 3 seconds more (the tracks are read from the moment the content is in, alongside the reference data), "Preparing the pages…", then it lands and fades out over the link's first page. A link that does not open fades out to its message.
- A recorded track that arrives after a map is showing (on a link, or from the app's sync) fades in over 400ms while the great circle it replaces fades out, on the flat maps and the globes. When a flat map's framing changes to take the track in, the map moves and zooms to the new view over 450ms, and its height follows, instead of jumping. A track there when the map first draws does not move, and changing the period redraws the map at once.

## Home

- Flights summary tiles: flights, distance, time, airports, airlines, aircraft.
- Sightings summary tiles: aircraft, sightings, airlines, families, type codes, special-livery aircraft.
- Most frequent airline / family / type for each.
- Recent activity: last 5 flights, last sighting session.
- Open issues count, with a link to Issues.

## Flights

**Figures (Decided, built).** Above the map, the period's figures as tiles, as on Home: flights and their distance, time in the air, the longest flight, the most flown route and the most flown airline. Pointing at the longest flight or the route shows it on the map. Home keeps its summary sentence.

**List.** Table with date, flight number, route, airline, type, registration, distance, duration, and a track icon (recorded track or great circle only; hovering it explains which, the source, and whether the track has gaps). A flight with no number (a private flight) is named by its registration there, in the flight page's header and pager, on maps' tooltips, on the Issues page and wherever else a flight is named by its number (`flightName` in core). Its flight number field stays empty. Filters by year, airline, airport, type. Search by flight number, airport or city, registration, airline or type, or by route: "SHA-PEK" (or "SHA PEK", "Shanghai - Beijing") finds it either way, "SHA > PEK" (or "SHA to PEK") one way. A code names only its airport, so "SHA" is not Pudong. The map above keeps the whole period in its frame while searching or filtering: the flights left out turn grey. `touchdown flights --search` reads it the same way (`packages/core/src/view/search.ts`). Beside the filters, when some flights have no recorded track: "N without a track (CSV)", the short list to send to someone who can find them ([23](23-tracks-and-maps.md), "Helping each other").

**Detail.** Map or globe (track or great circle; see Globe), all fields, the linked airframe with its other flights and sightings, findings for this record. Beside Edit and Delete: Add track, or, once the flight has one, a Track menu (Download as KML, Replace with a track file, Remove the track). A chosen file is checked against the flight and shown above the map with what it holds, or why it cannot be used, until the user saves it or cancels; saving or removing is an import the Import page's history can undo ([23](23-tracks-and-maps.md), "Sources").

**Special livery (Decided, built).** A flight on an aircraft in a special livery says so in its lead sentence ("on D-AXYZ, an Airbus A350-900 in its Centenary livery"), and a band between the sentence and the map gives the aircraft the stage: its reference photo beside the livery's name, the registration, type and airline, how many of the user's flights on it were in that livery and when it was photographed in it. The aircraft card below then leaves the photo out. The aircraft's page has the same band under its sentence, in place of the side photo, and its timeline shades the records in the livery and names it. A livery typed as "Centenary", "centenary" or "Centenary Livery" is one livery (`sameLivery` and `liveryName` in `packages/core/src/livery.ts`). The photo is the registration's latest on planespotters.net, which may show a later livery.

**Quick add (requirement F3).**
1. Enter flight number and date.
2. If a flight lookup is available ([13](13-reference-data.md)), prefill airline, airports, times, type, registration. Shown as suggestions. In practice this works only for flights in the last 10 days with an AeroAPI key, or during the flight through "capture during flight". For older flights the user types the registration.
3. Otherwise enter airports (autocomplete on IATA, ICAO, city, name).
4. Optional fields are collapsed under "More": seat, class, times, gate, livery, notes.
5. Every time field is a date-and-time input. The date part starts as the scheduled date (for landing: the date implied by the duration) and is always shown next to the time, so a takeoff after midnight is entered on the next day, not on the scheduled date.
6. Checks run as fields change; findings show inline.

## Sightings

**Figures (Decided, built).** Above the map, six tiles: the aircraft photographed (and how many are new to the log), the days out and their airports, the most spotted airline and type, the special liveries, and the busiest day.

**List.** Table with date, location, registration, operator, type, special livery, phase (every phase it was seen in, one per line). Same filters and search as flights. A row opens the aircraft's page, as every list of aircraft does; a sighting not yet matched to an aircraft opens the sighting itself. A sighting is edited from the aircraft page's timeline.

**Quick add (single).** Registration, then date and location (default: last used), then phase (one tap; tap more for every phase it was seen in). After the registration is entered, the app shows what it knows about the airframe (type, operator, previous sightings, "you flew on this aircraft on ..."). When the log has the aircraft in a special livery, it asks whether the aircraft still wore it (Q-SPOT-LIVERY); session add asks the same on each row.

**Session add (bulk).** For a spotting session with many aircraft: set date and location once, then add registrations one after another (type or paste a list). Each row resolves in the background; rows with findings are marked. A single session can have more than 100 sightings, so this flow matters.

**Photo link.** Optional field: paste a Google Photos share link. Shown as a plain link. (Google offers no way to embed or resolve these links.)

## Aircraft

**Figures (Decided, built).** Above the list: the aircraft in the log (all confirmed, or how many have no serial number yet, for the owner only), those flown on and how many of them were also photographed, those photographed, those in a special livery, and the aircraft flown on most.

**List.** Distinct airframes with type, current registration, operator, number of flights, number of sightings, first and last seen. An aircraft in a special livery has a capsule after its registration for each livery, named as on its page. Filters: all, flown on, flown and photographed, and special livery (a flight or sighting in one).

**Detail.** Facts (MSN, first flight, type, model), registration history, operator history, timeline of the user's flights and sightings, special liveries seen. An aircraft with a special livery in the log gets the livery band under its sentence (see Flights, "Special livery").

**Tools.** Merge airframes, split a registration period, set MSN, edit facts (stored as user values, see `field_provenance`). See [11](11-aircraft-identity.md).

**Facts and their sources.** Each fact says where it came from: "from OpenSky", "from Flightradar24" (linked to the page), "from your sheet", "entered by you". "Look it up" links open airfleets.net, aviation.flights, planespotters.net and Flightradar24 with the registration filled in. "Paste from a web page" reads the serial number, line number, first flight and delivery dates from text copied off one of those pages, shows what it found and warns when the page cannot be about this aircraft (it first flew after one of the user's records); "Save these" stores the values as the user's. See [13](13-reference-data.md), "Airframe facts".

## Airports

**Opened from** any map: clicking an airport dot, an airport label or a spotting location on the flat maps (Home, Flights, Spotting, an airport page) or on a globe opens `/airports/<id>`. On a flight page, the airport names in the header and the airports on the map link there too. Hovering an airport shows its name and the number of flights in the period.

**Page.** Follows the shared period control.
- Header: the airport code, city, full name, country, ICAO code.
- Lead sentence and facts: departures, transits, landings, the airport flown with most often, aircraft photographed (sightings and days), the first day the user was there.
- A transit is a landing at the airport followed by the user's next flight leaving it within 24 hours (the next day at most when times are missing). Its two flights count as one transit, not as a landing and a departure.
- Map or globe (see Globe) of the flights to and from the airport and the spotting dot; other airports on it open their own pages.
- Flights list, newest first, 20 per page, with a "Transit" pill on both legs of a transit.
- Aircraft photographed there, one row per airframe (times seen there, flights on it, last seen there), 30 per page.
- An airport the user added says so under the header ("An airport you added"), with "Edit", which opens the airport's form.

**Airports of your own** (Decided, built). An airport field (a flight's From and To, a sighting's and a spotting session's location) suggests airports by code, place and name. A code or a name the airports shipped with the app do not have loads the small airfields first ([13](13-reference-data.md), "Airports"). Still unknown, the hint under the field reads "Not a known airport code" with "Add as an airport…". On the Issues page, an unknown airport code has "Add EGLM as an airport…". Both open a dialog (the share dialog's card, 36rem wide):

- Code: what the record has, when it is three or four letters or digits. A code the app knows already is refused, naming the airport.
- Name, town or city.
- Position: latitude and longitude as a map gives them, in decimal degrees or degrees, minutes and seconds, with or without N, S, E and W (`parsePosition`). Under it, how far the nearest known airport is, so a wrong position shows.
- Country and time zone: set from the nearest known airport until the user chooses them, saying which airport gave the zone.

Saving links every flight and sighting that has the code, or what the field held, and no known airport, and says how many. A flight's times at it are stored with its UTC offset from then on. The airport is in the log (`airport_overrides`, [10](10-domain-model.md)), so it syncs and share links show it.

## Addresses

Pages of records have readable addresses made from what the record is, not from stored ids, so an address still works after the log is rebuilt from its sources (Decided).

| Page | Address | Made from |
|------|---------|-----------|
| Flight | `/flights/2025-03-14T0830-LHR-CDG` | Local takeoff date and time at the departure airport, then departure and arrival codes. Without a takeoff time: `/flights/2025-03-14-LHR-CDG-XY300` (flight day, route, flight number if any). |
| Sighting | `/spotting/2025-03-14-AMS-N1001X/edit` | Day, place, registration: one sighting per aircraft, place and day (Q-SIGHTING-UNIT). |
| Aircraft | `/aircraft/airbus-a320-99001`, `/aircraft/boeing-28470` | Maker and serial number, the airframe's identity ([11](11-aircraft-identity.md)), with the series for Airbus, which numbers each family from 1. Until the serial number is known: `/aircraft/N1001X-2024-03-01`, the registration it was first seen with and that day (what the provisional identity is made of). |
| Airport | `/airports/LHR` | IATA code, or ICAO when the IATA code belongs to another airport too. |
| Shared link | `/p/<id>`; pages inside a whole-log link follow a `#` | A random id, not made from the record ([32](32-modes-and-sharing.md)). |

- Neither the flight number nor the registration is the key. Flight numbers repeat (an airline often uses one number both ways, or for a shuttle flown several times a day); no one leaves the same airport twice in one minute, so the takeoff time is. Registrations rotate when an aircraft changes hands and are reused on other aircraft; the serial number stays with the airframe.
- A sighting keeps its registration in the address: it records one moment, and the registration at that moment does not change.
- If two records would get the same address, the later one gets `-2`, `-3`.
- Addresses ignore case. Old addresses still open their page: one made from a stored id, and an aircraft address made from a registration (bare, or with the day first seen) when only one aircraft in the log carried that registration. So an aircraft's address changes when its serial number becomes known, and the old one keeps working. An Airbus address also changes when its type becomes known, which gives its series; the old one does not stay.
- Editing a flight's takeoff time or route, or a sighting's day, place or registration, changes its address.

## Going back

Decided: Back shows a page as it was left. Forward does the same.

- Kept: the search text, filters and chips, sort, tab, page number, the custom view's choices, map layers and expanded sessions, and the scroll position.
- Kept per visit (each browser history entry), not per page. Opening a page from the navigation starts it fresh; going back to an earlier visit shows that visit as it was.
- A reload keeps them. They are held in the browser's session storage for the tab and never leave the browser.
- The period (year) is not part of this: it is one setting shared by every page (Period control).

- Custom view (a pivot, [24](24-statistics.md)): one sentence of choices ("Number of flights by airline split by family", swap and remove beside it), filter chips with a panel of values and counts, a table shaded by size with totals, whose every figure lists its flights or sightings under it, and saved views as chips.
- Airports and spotting locations by name with their code ("Amsterdam Schiphol (AMS)"), types as "Airbus A321neo (A21N)", routes by their codes ("AMS ⇄ MAD"; names made the list hard to scan). Words in full ("Aircraft types", "Seat position").

It fills in once, when they are all in, so nothing below it moves and its rows do not reorder as each track arrives.

## Globe

Decided: there is no separate map or globe page. Home and Flights show the period on a flat map; the globe sits where it adds something. The old addresses `/map` and `/globe` open Statistics.

| Where | Shows | Controls |
|---|---|---|
| Statistics, above the tabs | The period's flights (recorded track where there is one, great circle otherwise) and spotting locations | Flights and Spotting switches, airline filter, Expand |
| A flight page | That flight's route, framed on it, with its great circle dashed beside a recorded track | Map / Globe switch, Expand |
| An airport page | The period's flights to and from the airport and its spotting dot | Map / Globe switch, Expand |

- Map / Globe: a two-part switch at the end of the map's legend row. The choice is kept in this browser, like the theme, so every flight and airport page opens the way it was last left.
- Switching moves nothing: the legend row is the same for the map and the globe, and the globe takes the flat map's height. Expand sits inside the globe's box, in its top corner.
- In a page, the globe does not take over scrolling: the scroll wheel and vertical swipes move the page, a sideways drag turns the globe, and a pinch or Ctrl-scroll zooms. A vertical swipe that starts on the globe leaves it as it was. Zoom buttons and a "turn back" button sit in its corner.
- Expand shows the globe full screen (the browser's full-screen mode), where scrolling zooms. Collapse, Esc or Back on Android return to the page.
- Pointing at a route or an airport describes it; clicking opens its page. Clicking the globe itself never scrolls the page.
- Framing: the globe turns to the routes it shows and zooms in on them, but never so far that its edge leaves the view.
- Later: export as a figure (PNG/SVG) or video (MP4/WebM) for one flight, a date range or year, or all flights. See [23](23-tracks-and-maps.md).

## Import

Wizard: choose source → upload or pick file → column mapping (auto-detected for known formats) → review → commit.

Review screen:
- One row per record: parsed values, normalised values, resolved airframe.
- Findings from the deterministic checks.
- Agent suggestions if a check result was loaded ([22](22-agent-verification.md)).
- Per row: accept, edit, or skip. Per suggestion: accept or reject. Bulk accept by rule.
- Commit creates an ImportBatch. Import history lists batches with an undo button.

**Check with an agent** (Decided, built). A panel under the summary, above the row filters:
1. "Save the request" saves `touchdown-check-<id>.json` to the browser's downloads.
2. The command to run in a terminal in the Touchdown directory (the user's copy of the repository), with a copy button: `./touchdown check ~/Downloads/touchdown-check-<id>.json`. The agent, its rules and whether notes are sent are the CLI's settings on that computer ([22](22-agent-verification.md)). Before the steps, a note says what the Touchdown directory is and how to set it up once (`git clone`, `npm install`, an agent signed in and chosen with `./touchdown agent`), with a link to the README's "Set up".
3. "Load the result" reads the `.result.json` the command writes next to the request.
- Under the steps, a line says what is sent and what never is.
- Once a result is loaded, the panel says how many rows were checked and how many suggestions there are, how many are used or dismissed, and how many answers did not pass Touchdown's checks or got no answer. Buttons: use every high-confidence suggestion, show those rows, load another result, remove the check.
- An "Agent" filter shows the rows with suggestions; "Need a look" includes rows with suggestions not yet used or dismissed.
- Each suggestion sits under its row's findings: the field, the current value struck through, the suggested value, the reason, the confidence and where it comes from (the reference data, your other rows, what the agent knows). Use or Dismiss, and Undo after either. A row the agent doubts without a suggestion shows its note.
- Using a suggestion updates the row at once: its status, its findings and the summary are worked out again with the new value. In "Disagrees", a field the agent set is ticked and locked.
- A result from another file is refused. The same file chosen again (after a reload) takes the same result.

**Columns of a spreadsheet** (Decided, built). When the columns of a file are unclear, or rows cannot be read with what was worked out, a column step comes before the review: "The rows are: Aircraft you saw / Flights you took", then each column with three of its values and a select of what it holds ("Not used" included); unclear columns are shaded with the reason. "Read the rows" is enabled once the mapping can read rows (one column per field, a registration for sightings, a date and flight number or airports for flights). The layout is remembered in the browser; the review then says how the columns were read, with "Change the columns" ([21](21-import-export.md), "Source: any spreadsheet").

**The inbox waiting** (Decided, built). Files in the inbox of the user's storage (and, in development, `data/private/inbox/`) not imported yet, from `touchdown spot` and `touchdown add`, are listed above the file picker as "Waiting to be imported": the session's date and time (or "Added from the command line" and the time), how many flights and sightings are not in the log yet and which command made the file, Review and Discard. On every other page a note bar under the masthead says how many flights and sightings are waiting, with "Review and import" and "Not now" ([21](21-import-export.md), "Getting a session to the web app").

**An inbox file** (Decided, built). The file picker also takes the `.json` inbox file that `touchdown spot` or `touchdown add` writes ([21](21-import-export.md)). The review says the rows were filled and checked in a spotting session, and by which agent, or checked against the log by `touchdown add`. Beside Import, "Discard this file" deletes it from the inbox after a confirmation, and nothing goes into the log (built). The agent check panel is not shown. What the session left open shows as a warning on its row, and "Need a look" opens on those rows. A check request or result chosen here by mistake gets a message saying where it belongs.

**A change file** (Decided, built). A file from `touchdown edit`, `delete` or another changing command ([34](34-command-line.md), "Change files") opens on the Import page in its own review, from the list, the bar or the file picker: each change with what it is about, a note when it has nothing left to do or its record was changed since (left out unless ticked), and its values before and after; the findings the changes taken would bring; "Import N changes" and "Discard this file". The import is one batch in the history ("N changes made"), undone like any import. The waiting list and the bar count changes with the records ("1 change to make").

## Issues

Fields changed on two devices come first (Decided, built; [12](12-storage-and-sync.md), "Sync algorithm"): "Changed on two devices", one item per field, with the record it belongs to, the value in the log (and on which device and when it was made, or "changed since") and the other change. "Keep it" closes it; "Use the other" sets the other value. An entry deleted on one device and changed on another (or tagged, or given a photo link) reads "Deleted and changed", with "Keep the entry" and "Delete it". A value as typed and its normalised form are one item. What two devices made twice is settled without asking where nothing is lost ([12](12-storage-and-sync.md), "Settling what two devices made"); only what needs a choice is listed here. The choice syncs like an edit, so it closes on every device. Private values show as "(private)". They count in the lead sentence, the Open tab and the masthead's issues badge.

Then all open findings grouped by rule. Each has the records involved, the suggested fix, and "accept warning" (IssueAck). An unknown airport code has "Add … as an airport…" (see Airports). A second tab lists accepted warnings so they can be reopened.

Order (Decided, built): groups by severity (errors first), then in the fixed order of the rules in `packages/core/src/rules`; within a group, newest record first. The order does not depend on how many findings a group has, so accepting or fixing one brings the next into its place and the groups do not move.

## Getting started

Built: `/guide` (`pages/Guide.tsx`), behind the sign-in like every page of the app, linked from the empty log and the More menu (as "Guide"). For someone new, such as a friend the owner invited: the three modes (with the one the user selected), bringing in a myFR24 export step by step (with a link to myFR24's export page), a spreadsheet, adding flights and sightings, recorded tracks, Issues, sharing and taking the log elsewhere, each with a link to the page that does it. Each step is a short text beside a diagram of what it does, drawn from the app's own parts: the three modes side by side as a table (where the log is kept, whether other devices sync, share links, signing in to Google, whether Touchdown's server can open the log), with the selected mode's column in the selection container, the myFR24 import as numbered boxes matching the text, a spreadsheet's columns as Import's column step reads them, the Add menu, a route's great circle and recorded track as the flight map draws them, a finding with its fix, a share link's way to its page, and what Settings › Data makes. The diagrams repeat the text, so screen readers skip them. Kept current (Decided): each new or changed feature is checked against it, and added to its text and diagrams when a new user needs to know it.

## Language

Built (G12): every word the web app, the share and sign-in pages, the CLI and the server show is a message in `packages/i18n/messages/<language>/`, looked up by key (`packages/i18n/README.md`). UK English is the source. The web app and the share and sign-in pages are also in American English, German, Simplified Chinese and Traditional Chinese for Taiwan (`en-US`, `de-DE`, `zh-CN`, `zh-TW`, built). The CLI and the server stay in UK English.

| Part | Rule |
|------|------|
| Messages | A subset of ICU MessageFormat, the format translation tools read: named arguments, plural forms by the language's own rules, choices (`select`), and tags for bold text and links. One message for each whole sentence, never one put together from pieces, so a translator can change the word order (Decided). |
| Choosing the language | The first of the browser's languages the interface has in some form (Chinese of Hong Kong and Macao gets Traditional Chinese, English of Australia gets UK English), or a language chosen in Settings, which is kept in the log (`settings.language`) for every device, like the theme. It is put in place before the first page is drawn. Changing it reloads the page. A language chosen on another device is used from the next load, not by reloading a page in use. Each browser keeps a copy of the choice for the pages drawn before the log is open: the loading screen and the sign-in pages. Settings lists the languages by the names they give themselves. The share page uses the viewer's language, never the owner's: the language their own account chose when they are signed in to the site, else the one chosen in this browser, else the browser's languages. The CLI stays in UK English whatever the terminal's language: its own messages are not translated, and its reports would mix two languages (Decided, built). |
| Translations | German and Chinese address the user informally (du, 你). en-US has only the messages spelt differently, and the rest come from UK English. Chinese is set in the system's Chinese face for its script, with Latin letters and figures in Source Sans 3. A label put inside a sentence is lower-cased only in English. Airports, the places they serve and airlines are shown by their names in the language where Wikidata has one, and the makers of aircraft types where the language has its own name for them ([13](13-reference-data.md), "Names in other languages"), else in English. Notes for each language and the words for Touchdown's terms: `packages/i18n/GLOSSARY.md` (Decided, built). |
| Numbers, months, weekdays, lists | In the chosen language, from the browser's formatting (Intl) (Decided). |
| Date format | A choice of its own, but its choices come from the language (Decided): the language's own way ("15 Mar 2025" in UK English, "2025年3月15日" in Chinese), the other regional ways of the same language where they differ ("Mar 15, 2025" for English), and ISO 8601 ("2025-03-15") in every language. Month and weekday names stay in the language. Kept in the log beside the language (`settings.dateFormat`), and used at once on every device: pages drawn after use it. A share link shows dates in the viewer's own choice. |
| Times | 24-hour in every language and date format, as aviation writes them (Decided). |
| Kept in English | The agent's prompts, file formats (CSV and spreadsheet headers, the myFR24 columns), the column names an import recognises, command names and flags (Decided). |
| The server | Its errors are messages too, answered in UK English for now. Picking the request's language is Open (Q-I18N). |
